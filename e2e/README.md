# End-to-end tests (phase 0 baseline)

These tests run the current v1 code (`easyssh-core`, which spawns the system
`ssh`, `sftp` and `scp`) against real OpenSSH servers in Docker. They record
what v1 does today so that later rewrites can be compared with it. They run on
Linux only, in the CI job "End-to-end (Linux)". Windows and macOS keep unit
tests and the manual smoke test in `RELEASING.md`.

## Run locally

Needs Docker with Compose, OpenSSH client tools (`ssh`, `sftp`, `scp`,
`ssh-keygen`) and Rust.

```sh
e2e/prepare.sh                              # throwaway key in e2e/.keys (git-ignored)
docker compose -f e2e/docker-compose.yml up -d --build
e2e/wait-ready.sh                           # waits for an SSH banner on 2222 and 2223
cargo test -p easyssh-e2e -- --ignored --test-threads=1
docker compose -f e2e/docker-compose.yml down
```

Every test is `#[ignore]`, so a plain `cargo test --workspace` only compiles
them.

## The servers

| Container | Host port | Notes |
| --- | --- | --- |
| `target` | `127.0.0.1:2222` | also runs an echo service on its `127.0.0.1:7777` |
| `bastion` | `127.0.0.1:2223` | reaches the target as `target:22` |

Both have `keyuser` (public key only) and `pwuser` (password only, the public
test password `e2e-test-password`). Everything under `e2e/` is test-only. The
key pair is generated by `prepare.sh` and never committed.

## Isolation from your real SSH setup

The tests never read your `~/.ssh/config` or `known_hosts`. OpenSSH takes the
home directory from the password database, not from `$HOME`, so setting `HOME`
is not enough. Each test instead creates a temporary directory with a
generated config and wrapper scripts for `ssh`, `sftp` and `scp` that run the
real tool with `-F <that config>`. The wrappers go first on `PATH`, which is
how the core finds the tools. `HOME` points into the temporary directory too
and `SSH_AUTH_SOCK` is unset. The config defines the aliases `e2e-target`,
`e2e-bastion`, `e2e-target-internal`, `e2e-target-via-bastion` (ProxyJump) and
`e2e-target-pw`, with `StrictHostKeyChecking accept-new`, a temporary
`UserKnownHostsFile` and `IdentitiesOnly yes`. The test
`config_is_isolated_from_the_real_home` checks this.

Because tests change process environment variables, a global lock serialises
them; CI still passes `--test-threads=1`.

Every blocking wait has a timeout, so a broken server fails a test instead of
hanging CI.

## Passwords

v1 sends passwords through `SSH_ASKPASS` (`src-tauri/src/askpass.rs`). That
module needs a Tauri `AppHandle`, so the tests use a small shell helper with
the same environment (`SSH_ASKPASS`, `SSH_ASKPASS_REQUIRE=force`, `DISPLAY`)
and check that OpenSSH really asked it for the password.

## Known v1 failures

No test is currently marked as a known bug. If one is added, name it
`known_bug_*`, give it `#[ignore = "known v1 bug: ..."]` and skip it in CI with
`--skip known_bug_`; remove both again once it is fixed.

### Fixed in 1.0.2: file transfers to password-only hosts

`sftp::spawn_transfer` starts `sftp -b -`. `-b` makes sftp pass
`-obatchmode yes` to ssh, so ssh never asked for a password and `SSH_ASKPASS`
was never called; against `pwuser` the upload ended with `Connection closed`
and the askpass log stayed empty (CI run 43990861805). The fix passes
`-oBatchMode=no` before `-b`: sftp adds its `-obatchmode yes` at the position
of `-b`, and ssh keeps the first value of an option (checked with
`sftp -S <fake ssh>`, which prints the ssh arguments). Errors are still
reported through the exit code of batch mode.

### Listing a missing directory is timing dependent (observed, not fixed)

`SftpSession::list` of a directory that does not exist returned an empty
list in one CI run and `Failed("Can't ls: ... not found")` in the next, for
the same code. The error text arrives on standard error, and `run_for`
collects late standard-error lines for only 20 ms after the command's marker.
When the line is later than that, the command looks successful. The test
accepts both outcomes. Not investigated further: a late line could also be
attributed to the next command, but no test has demonstrated that.
