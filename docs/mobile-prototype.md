# Mobile prototype (phase 7)

Status: **evidence for the owner's decision**. The owner asked for one week to
prove Tauri mobile viable before committing to it. This page is what that week
produced: what runs, what CI measured, what blocks a release, and a
recommendation. Architecture background: [architecture-v2.md](architecture-v2.md)
§2 (the engine runs in the app process on mobile) and §12 (phase 7).

Nothing here was run on a phone. The only machines were CI runners and a
Linux sandbox without Android or Xcode, so "works" means "builds, passes its
tests and renders in the browser preview", and every statement about device
behaviour is marked as unverified.

## Update: the shared engine and the phone's feature set

After the prototype the connection registry, SFTP and tunnels moved from
`easysshd` into `easyssh-engine` behind one event trait (`EventSink`, a closure
works), and the sync service moved with them. The daemon wraps the same code in
its socket protocol; the phone calls it in-process. What that gives the phone:

- **One connection per host.** A terminal, the file browser and a port forward
  on the same host share one authenticated connection, so the person signs in
  once (`registry.rs`, tested against the OpenSSH container in
  `crates/easyssh-e2e/tests/mobile_engine.rs`).
- **Files.** Browse a folder at a time, make folders, rename, delete (through
  the confirm dialog), upload and download. The web view cannot hand the engine
  a path, so an upload is staged first: the picked file is sent in 512 KiB
  chunks (`stage_begin`, `stage_chunk`, `stage_finish`) into the app's cache and
  the engine uploads that copy, which is removed when the transfer ends.
  Downloads land in the cache and end in the share sheet or Downloads (Android
  `AnixNative`, iOS `navigator.share` with the bytes). Cancelled transfers are
  reported and leave no partial file. Only files are transferred on the phone,
  not folders.
- **Forwards.** Local forwards (`ssh -L`) on the phone's loopback interface,
  with a switch and the failure reason. Remote forwards and SOCKS proxies stay
  on the desktop and read correctly when they sync in.
- **Jump hosts.** A host can be reached through another saved host, chosen from
  a list; the hop is opened on the shared connection and asks its own host key
  and password questions.
- **Host list.** Group (found by name ignoring case, or created), tags,
  favorites, a jump host, search by name, address, group or `#tag`, and a `⋯`
  menu on each row (terminal, files, edit, favorite, delete).
- **Sync.** Sign up and sign in to your own server, sync now, the devices of the
  account and the safety number. HTTPS verification uses the platform trust
  store (`rustls-platform-verifier`; on Android its Kotlin half comes from the
  Gradle repository in `src-tauri/gen/android/build.gradle.kts`, at the version
  `Cargo.lock` pins). Team vaults and host history are desktop screens for now
  and answer `unavailable`.
- **Navigation.** A tab bar with Hosts, Forwards and Sync; a host opens as a
  terminal or a file browser, and the terminal stays alive while the files are
  on top of it.

Still open: the device key store (Keystore and Keychain). The vault hooks are
marked `HOOK(mobile-vault)` in `mobile.rs` and `hosts.rs`: until they exist the
phone has no saved passwords or keys (every connection asks) and the sync
sign-in lasts only until the app closes. Nothing in this update was run on a
device; the Android and iOS jobs check that it builds.

### Engine crates

All six crates the app needs compile for `aarch64-linux-android` and
`aarch64-apple-ios` with no source change besides one `unused_variables`
silence in `easyssh-core` (the external-terminal launcher has no body on
mobile), and the new FIDO2 hardware-key backend (`ctap-hid-fido2`, HID) is
gated to Linux and macOS targets so it stays out of Android and iOS: `easyssh-core`, `easyssh-ssh`, `easyssh-store`, `easyssh-crypto`,
`easyssh-vault` and the new `easyssh-engine`. CI checks them on both targets
(`logs-android/android-engine-check.log`, `logs-iOS/logs/ios-engine-check.log`).

Desktop-only dependencies are kept out of the mobile build by target tables in
`src-tauri/Cargo.toml` (`cfg(not(any(target_os = "android", target_os = "ios")))`):
`easysshd`, `portable-pty`, `easyssh-unlock`, the vault's `os-keyring` feature,
`easyssh-telemetry`, `easyssh-ai`, the dialog and opener plugins. `serialport`
lives inside `easysshd`, so it never reaches the mobile build; the OpenSSH
wrapper in `easyssh-core` still compiles there (it is plain `std::process`), but
nothing on mobile calls it. The Tauri capabilities are split
(`default.json` for desktop, `mobile.json` for Android and iOS) because
permissions of plugins that are not compiled in are rejected.

### Why `easyssh-engine` and not "all of easysshd's engine"

`easysshd`'s engine is tied to things a phone does not have: it plans each
connection with `ssh -G`, falls back to the system OpenSSH, prompts through the
daemon's loopback askpass hub, and shares connections between terminal, files
and tunnels through a registry that the daemon owns. Moving all of that would
touch the desktop path the whole product stands on, for a prototype.

(This was the first cut; the registry, SFTP and tunnels have since moved, see
the update above. The text below is how the prototype was scoped.)

So the extraction is the smallest one that gives the mobile app a real engine
and leaves the desktop unchanged: `known_hosts` (store-backed host keys, moved
verbatim with its tests and re-exported from `easysshd::engine::known_hosts`)
and `error_code`. The prompt broker, the shell pump and the host list are new
and small. The desktop daemon keeps its own copies of the prompt code; the
duplication is two small types and goes away when the registry moves.

At the prototype the mobile engine did not yet do one shared connection per
host, SFTP, tunnels or jump hosts; it does now. Saved passwords and keys are
still missing.

## What works

Verified in CI or in the browser preview:

- The engine opens a russh shell, asks for the host key and the password
  through the same `hostkey` and `askpass` events the desktop dialogs already
  handle, runs a command and reports the exit code (e2e, Linux, real OpenSSH).
- The Android debug APK builds with the runner's SDK and NDK; a release APK
  builds unsigned. The app library builds for the iOS simulator and
  `tauri ios build --debug --target aarch64-sim` produces `AnixOps SSH.app`
  without signing.
- The touch UI: host list with 44 px two-line rows, search, add host, terminal
  with a key bar (Esc, Tab, sticky Ctrl, arrows). Under 834 px (`md`) the list
  and the terminal are screens; from 834 px up (a tablet) they sit side by side.
  Light and dark, safe-area insets, inputs at 16 px or more, and a screenshot
  check that fails the frontend job when any button or input is under 44 px.
  The screenshots are `mobile-*` in `ci-results`.
- The key bar's bytes (`src/lib/mobileKeys.ts`) are unit tested: arrows follow
  the terminal's cursor-key mode, Ctrl turns the next letter into a control
  character, Ctrl with an arrow sends the xterm modifier form.

Not verified on any device: typing with a real soft keyboard, scrolling and
selecting in xterm.js by touch, the keyboard covering or resizing the view,
safe-area values in a real Android WebView, how the app behaves when the system
suspends it, TLS from the sync client, and every performance number that is not
a build number.

## Blockers and findings

### Background execution

A phone does not keep a TCP connection alive for an app that is not in front.
Android may kill the process and in any case suspends the network under Doze and
App Standby; a foreground service with a notification keeps a process alive for
a while but is a policy risk on Google Play for an SSH client and still does not
survive Doze for long. iOS suspends the app seconds after it leaves the screen
and offers a short background task, nothing like a session.

Consequence: a session lives as long as its screen. The prototype closes the
session when the terminal screen goes away, and when the connection dies it shows
"Reconnect", which opens a new shell. The SSH protocol has no resume, so scrollback
and running programs are lost. The honest product answer is not on the phone:
reattach to `tmux` or `screen` on the host (an opt-in "attach or create" command
when the shell opens), or the relay through the sync server that §2 describes for
taking over sessions. The phone's side is fast reconnect, and it needs a timeout
policy so a locked phone does not hold ten half-open sockets.

### Device key: Keystore and Keychain

The desktop vault keeps the device key in the OS keychain through the `keyring`
crate behind the `os-keyring` feature. That feature is off in the mobile build,
and the prototype opens the store with a cipher that refuses every secret, so
**saved passwords and keys do not work on mobile yet**; the user types the
password at each connection. A real build needs an implementation of the vault's
key store for the Android Keystore (hardware-backed, through JNI or a Kotlin
plugin; `keyring` has no Android store of its own) and for the iOS Keychain (the
Apple store the desktop macOS build already uses is the starting point). The
vault trait is the seam; the crypto crate already separates the key store from
the record encryption.

### Biometric unlock

`tauri-plugin-biometric` is the official plugin for BiometricPrompt and Face ID /
Touch ID. It was not integrated: the prototype stores no secret to protect. A gate
that only asks "is this the owner?" before showing the vault is not the same as a
key that cannot be released without the sensor; the second needs the Keystore or
Keychain item created with user-authentication required. Plan for the second, and
treat what the plugin offers beyond `authenticate` as something to check against its
current API before relying on it. The desktop already has the same shape
(`easyssh-unlock`: a platform gate over the vault), so the mobile gate is a third
backend for it.

### IME and the soft keyboard in xterm.js

xterm.js receives input from a hidden `textarea`. On touch devices that is where
the trouble is, and none of it could be tested here:

- Predictive text and autocorrect (Gboard, the iOS keyboard) send composed text
  and replacement events instead of key events. The prototype turns off
  `autocapitalize`, `autocorrect` and `spellcheck` on the textarea; whether Gboard
  still composes words, and whether backspace behaves on an empty field, has to
  be tried on a device.
- The keyboard has no Esc, Tab, Ctrl or arrows. The key bar sends them; it keeps
  focus in the terminal by swallowing the pointer-down, so the keyboard does not
  close when a key is pressed. Sticky Ctrl applies to the next typed key. There
  are no function keys, Home/End, Page keys or Alt/Meta yet, and no key repeat for
  held arrows.
- Layout under the keyboard: iOS covers the page without resizing it, Android
  may or may not resize it. The app sizes itself to `visualViewport.height`, so
  the key bar should sit directly above the keyboard in both; this is untested.
- Touch selection, long-press copy, paste and scroll in xterm.js are weak: it has
  no touch selection handles. Copy and paste need a small custom UI (the clipboard
  plugin is already in the mobile build).
- Hardware keyboards on tablets (the design repo's keyboard rules apply when one
  is attached) work through the same textarea; the desktop shortcut layer is not
  wired in the mobile UI.

If xterm.js proves too weak on touch, the fallback is a native terminal widget
fed by the same engine; the engine and host list are not affected.

### No SSH agent

There is no `SSH_AUTH_SOCK` and no OpenSSH named pipe on a phone, so the
authentication chain is a key held in memory (from the vault), keyboard-interactive
and password. The engine already works that way (`AgentSource::Disabled`). Agent
forwarding, the 1Password agent and FIDO2 hardware keys have no path yet; security
keys over NFC or USB would need platform code. Keys reach the phone through the
encrypted sync (phase 5), which is also the answer to "how do my hosts get here":
a phone has no `~/.ssh/config` to import, so the prototype's only inputs are typing
a host in and, later, sync.

### Other findings

- The sync client (`easyssh-sync`, a dependency of the store) builds for Android
  and iOS, but its HTTPS stack verifies certificates through the platform on Android,
  which needs an initialisation call and a small Kotlin component from the app
  before the first request. Not done; sync on mobile is blocked on it.
- The generated Android project targets a very new SDK (compileSdk 37, AGP 9.3.1,
  Gradle 9.6.1); it built on the runner's image without changes. The activity enables
  edge-to-edge, so the web view draws under the system bars; the UI uses
  `env(safe-area-inset-*)`, which has to be confirmed in the Android WebView.
- Debug builds are unusable as a size reference (239 MiB, almost all debug
  symbols); use the release number.
- The iOS project (`src-tauri/gen/apple`) is generated on macOS only, so it was
  produced by the iOS CI job and checked in from there (the job regenerates it
  only when the folder is missing).
- Telemetry, AI, serial ports, local shells, split panes, snippets, tunnels and
  file transfer are desktop only in this prototype. The web view's error reporter
  calls `telemetry_report_frontend`, which is a no-op on mobile.

## Recommendation

**Commit to Tauri mobile, Android first, with iOS built in the same CI from the
start, and gate the full phase on one device test.**

Reasons:

1. The risky half, the engine, is already portable. Six crates built for both
   mobile targets unchanged, and a russh shell ran end to end through the same
   prompt events the desktop uses. Nothing in the engine pushed toward a different
   stack; every alternative (Kotlin and Swift, Flutter) would still embed this Rust
   engine over FFI and still have to solve the same platform problems below.
2. The pipeline already produces installable artifacts from the one repo: a
   13.8 MiB release APK and an unsigned iOS simulator app, in about 11 and 13
   minutes, with no signing and no extra infrastructure. That is a fair size for an
   SSH client and leaves room for the features above.
3. The UI carried over. Tokens, the button family, the dialogs for passwords and host
   keys, i18n and the terminal theme were reused; the touch path is about 650 lines of TypeScript,
   and the 44 px rule is enforced by a screenshot check, not by review.
4. The blockers are product problems, not framework ones. Background limits, the
   Keystore, biometrics and the missing agent are the same in any framework; their
   answers (tmux reattach, hardware-backed key store, sync for keys) are mostly
   decisions plus well-bounded platform code.

Where Tauri mobile is the risk: **terminal input and selection on touch**, through
xterm.js, and the maturity of the Tauri Android and iOS plugin story for the
Keystore, Keychain and biometrics. Neither could be judged without a device, so
the commitment should carry a gate.

**Gate before the rest of phase 7** (about a week, a person with an Android phone
and an iPhone): type a realistic session through the key bar with Gboard and the iOS
keyboard (vim, tmux, `ctrl-c`, history search, Chinese input), rotate the phone,
background and resume the app, and judge the result. If typing is not good enough
after a day of fixes to the key bar and viewport handling, switch the terminal widget
and keep everything else. If the plugin work for the Keystore turns out to need more
than the Kotlin shim assumed, that changes the schedule, not the choice.

## What is left for a real mobile release

In rough order:

1. Run it on devices and fix what the gate finds (IME, keyboard layout, touch
   selection and copy, safe areas, rotation, tablets).
2. ~~Move the connection registry, SFTP and tunnels into `easyssh-engine`.~~
   Done, see the update at the top.
3. Vault on mobile: Android Keystore and iOS Keychain key stores, biometric
   unlock, auto-lock on background, saved passwords and keys, the first-run flow.
4. Sessions under background limits: reconnect policy, a "attach to tmux" option per
   host, optional relay through the sync server, a foreground notification only if
   the policy allows it.
5. Sync on mobile: platform certificate verification and sign-in are done; keys
   need the vault (item 3), team vaults and host history need phone screens.
6. Terminal toolbar completeness: function keys, Home/End/Page, Alt, key repeat,
   a customisable bar; selection and clipboard UI; font size gestures.
7. Release engineering: Android signing and the Play listing (including the
   foreground-service and "SSH client" policy questions), iOS signing, TestFlight,
   an app-store build in `release.yml`, x86_64 and armv7 split decisions,
   crash reporting with consent on mobile.
8. Accessibility pass (screen readers, dynamic type), and the design repo's
   phone patterns for settings and the empty states, which the prototype only
   approximates.
